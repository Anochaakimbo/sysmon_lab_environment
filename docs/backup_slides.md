## B1 — "ทำไม accuracy ถึงเป็นเท่านี้ / มันสูงจริงหรือเปล่า"

## B3 — "พิสูจน์ได้ยังไงว่าที่เก็บมาเป็นพฤติกรรมมัลแวร์จริง"

| ระดับ | จำนวน | % | ความหมาย |

| **PARENT** | 168 | 15.0% | `ParentCommandLine` เป็นคำสั่งของ test |

## B4 — "label มายังไง"

**สไลด์: lineage labeling**

1. seed = process ที่ถูกรันจาก `/tmp/lab_sandbox` (Linux) / `C:\lab_sandbox` (Windows)
2. ไล่ `ParentProcessGuid` ลงไปหาลูกหลานทั้งหมด
3. ทุก event ของ process ในสายนั้น = `label 1`

**ทำไมไม่ใช้ "ทั้ง session ที่รันมัลแวร์ = malicious"**
วัดแล้ว: session mode ให้ malicious 100% ทั้งที่ lineage บอกแค่ 8.9%
→ ถ้าใช้ session mode โมเดลจะเรียน "ช่วงเวลา" ไม่ใช่พฤติกรรม

**ข้อจำกัดที่ต้องยอมรับ**: `label=1` แปลว่า "สืบสายจาก sandbox"
ไม่ได้แปลว่า event นั้นเป็นมัลแวร์ในตัวเอง → จึงต้องมี B3

## B5 — "รวม Linux กับ Windows แล้วโมเดลไม่แอบใช้ platform เป็นทางลัดเหรอ"

**สไลด์: platform leakage — ยังมีอยู่ ยอมรับตรงๆ**

ให้ RF ทำนาย platform ด้วย feature ชุดเดียวกับที่ใช้ตรวจมัลแวร์ (32 ตัวสะอาด):

```
accuracy 0.9979   (ทายมั่วได้ 0.7592)
feature ที่บอก platform มากสุด: pcmd_len 0.612, cmd_len 0.145, dur_s 0.053
```

→ **โมเดลยังแยกแพลตฟอร์มได้เกือบสมบูรณ์** ตัวการคือความยาว command line
ซึ่งเป็นตัวเดียวกับที่ทำ harness leakage (B6)

**แต่**: เทรนแยกฝั่งแล้วผลไม่ได้แย่ลง แปลว่าไม่ได้พึ่งทางลัดนี้เป็นหลัก

| ชุดข้อมูล | n | acc | F1 |
|-----------|---|-----|-----|
| รวมสองฝั่ง | 23,971 | 0.9491 | 0.9241 |
| Linux อย่างเดียว | 18,302 | 0.9496 | 0.9200 |
| Windows อย่างเดียว | 5,669 | 0.9594 | **0.9530** |

**ทางออกที่เลือก**: รายงานทั้งแบบรวมและแบบแยก ให้ผู้อ่านตัดสินเอง
(ตรงกับทางเลือกที่ 3 ที่วางไว้: "แยกเทรนแล้วเทียบผล")

## B6 — "โมเดลเรียนอะไรกันแน่"

**สไลด์: harness leakage — ข้อจำกัดที่ใหญ่ที่สุดของงานนี้**

```
ความยาว CommandLine  median:  benign 22  vs  malicious 76
Linux   18 vs 51        Windows  34 vs 94

ใช้เงื่อนไข "ความยาว > 79" อย่างเดียว ไม่ต้องมีโมเดล  ->  accuracy 0.7603
(ทายคลาสใหญ่อย่างเดียวได้ 0.6619)
```

**สาเหตุ**: Atomic Red Team เรียกทุกอย่างผ่าน PowerShell พร้อม argument ยาว
ส่วน benign เป็นคำสั่งสั้น → ความยาวกลายเป็นลายเซ็นของ *เครื่องมือทดสอบ*

**ทางแก้ที่เลือก**: ทำ benign ให้มีคำสั่งยาวพอกัน — **ไม่ใช่ตัด CommandLine ทิ้ง**
เพราะ CommandLine คือสิ่งที่เปเปอร์ไม่มีและเป็น contribution ของงานนี้

พูดเองก่อนโดนถามจะดูรอบคอบกว่ามาก

## B7 — "ทำ feature selection ไหม / ทำไมใช้ feature เท่านี้"

**สไลด์: ทำแล้ว 3 วิธี ผลคือ PCA ไม่ช่วย**

**1. PCA sweep n=1..30 (เลือกจาก validation ที่แยกจาก test)**

| level | n ดีสุด | test F1 | ไม่ใช้ PCA |
|-------|---------|---------|-----------|
| process (35) | 18 | 0.9575 | 0.9579 |
| event (48) | 29 | 0.9355 | **0.9512** |

n ที่ชนะเกือบเท่าจำนวนเต็ม = PCA ไม่ได้รวบอะไร และที่ event-level ทำให้แย่ลง
**เหตุผล**: feature ผ่าน label encoding / ความยาวสตริงมาแล้ว
ไม่มีความสัมพันธ์เชิงเส้นให้ PCA รวบ (ต่างจากเปเปอร์ที่มีแพลตฟอร์มเดียว)

**2. greedy backward elimination** → ตัดได้ 30/35 และ 44/48 โดยเสีย F1 ไม่ถึง 1%

**3. ตัด feature ที่รั่ว 6 ตัวออก** (`--drop-derived`)

| ตัดอะไร | เหตุผล |
|---------|--------|
| `CurrentDirectory` | `/tmp/lab_sandbox` = malicious **100%** ← seed dir ของ labeler เอง |
| `ancestor_depth` | มาจาก lineage tree เดียวกับที่สร้าง label |
| `img_len` | เปเปอร์ตัด `Image` เองเพราะ *"direct association with the target variable"* |

## B8 — "unsupervised ทำไมต่ำกว่าเปเปอร์มาก (0.71 vs 0.975)"

**สไลด์: เพราะโปรโตคอลของเปเปอร์ทำให้ baseline สูงมากอยู่แล้ว**

โปรโตคอลเปเปอร์ (Fig. 4): เทรนด้วย benign, เทสด้วย benign ที่เหลือ + malware ทั้งหมด
→ **test set เป็น malware 83%**

| model | prec | rec | F1 | AUC |
|-------|------|-----|-----|-----|
| **LOF ของเรา (โปรโตคอลเดียวกับเขา)** | 0.976 | 0.805 | **0.882** | **0.917** |
| LOF ของเปเปอร์ | 0.958 | 0.993 | 0.975 | ไม่รายงาน |
| **baseline "flag ทุกแถว"** | 0.832 | 1.000 | **0.908** | — |

**อ่านบรรทัดสุดท้าย**: detector ที่ตอบว่า "ผิดปกติ" ทุกแถวโดยไม่คิดอะไรเลย
ได้ F1 **0.908** สูงกว่าโมเดลเกือบทุกตัว

⚠️ One-Class SVM ของเปเปอร์ recall = **1.0000 พอดีเป๊ะ** precision 0.7411
≈ สัดส่วน malware ใน test set ของเขา → **นั่นคือ detector ที่ flag ทุกแถว**
และ LOF ของเขาที่ใช้ **feature เดียว** ได้ F1 0.9778 = สัญญาณของ feature ที่รั่ว label

→ เราจึงรายงาน **AUC คู่เสมอ** (ไม่ขึ้นกับสัดส่วนคลาส) และพิมพ์ baseline คู่ทุกตาราง

| 1 | ProcessCreate | 28.7% | 29.5% ✅ ใกล้มาก |

## B13 — "ทำไมใช้ Atomic Red Team ไม่ใช้มัลแวร์จริง"

**สไลด์: เหตุผลด้านความปลอดภัยและการทำซ้ำ**

1. **map ATT&CK ตรง** — อ้างอิงในธีสิสได้ว่า event นี้มาจาก technique ไหน (ดู B3)
2. **ทำซ้ำได้** — คนอื่นรัน `Invoke-AtomicTest T1486 -TestNumbers 5` ได้ผลเดียวกัน
   มัลแวร์จริงเปลี่ยนพฤติกรรมตาม C2 / วันที่ / sandbox detection
3. **ไม่ทิ้งเครื่องมือที่ใช้นอกแล็บได้** — payload ที่เขียนเอง (backdoor, encryptor)
   เปลี่ยน IP แล้วใช้จริงได้ทันที ไม่ควรมีในรีโปของธีสิส

**มาตรการควบคุม**:
- deny list: `T1490` `T1485` `T1561` `T1529` `T1491` (ทำลายข้อมูล / ปิดเครื่อง)
- ทุกอย่างอยู่ใน sandbox directory + revert snapshot ทุกรอบ
- `check_scenarios.py` ตรวจ 6 อย่างก่อนเก็บทุกครั้ง (exit 1 ถ้าเจอปัญหา)

## B14 — "ปิด Windows Defender แล้วผลเปลี่ยนไปแค่ไหน"

**สไลด์: ต้องบันทึกว่าปิดอะไรไป**

Tamper Protection ทำให้ `Set-MpPreference -Disable*` ถูกย้อนกลับเงียบๆ
ตรวจด้วย `Get-MpThreatDetection` พบว่า Defender บล็อก command line ของ test ที่โหลดไฟล์

| | Defender เปิด | Defender ปิด |
|---|---------------|--------------|
| NetworkConnect รวม | 77 | 121 |
| **NetworkConnect malicious** | **0** | **6** |
| events รวม | 1,776 | 1,894 |
| FileCreate %mal | 46.2% | 56.4% |

**ถ้าไม่ปิด**: `NetworkConnect` จะกลายเป็น "benign เสมอ" = leakage ตรงๆ
→ ต้องเขียนในธีสิสว่าปิด Defender และ Tamper Protection เพราะกระทบ event ที่เก็บได้

## B15 — "มีอะไรที่พังแล้วไม่รู้ตัวบ้าง" / คำถามเชิงระเบียบวิธี

**สไลด์: silent failure ที่เจอและวิธีป้องกัน**

| อาการ | ผลที่เกิด | ป้องกันด้วย |
|-------|-----------|-------------|
| ART module import ไม่ติด | scenario exit 0, ได้ CSV 18,072 แถว **แต่ไม่มี atomic ทำงานเลย** | `Setup-Sandbox` throw ถ้าไม่เจอ module |
| Tamper Protection ย้อนค่า | NetworkConnect malicious = 0 | `Assert-DefenderOff` throw |
| `--duration` ไม่มีผลฝั่ง Windows | benign_win ได้ 528 แถว เทียบ Linux 5,330 | repeat loop + พิมพ์ "รวม N รอบ" |
| `pandas 3` เปลี่ยน dtype เป็น `str` | 27 คอลัมน์กลายเป็น −1 เงียบๆ โมเดลยังเทรนผ่าน | `assert_matrix_sane()` throw ถ้า feature คงที่ > 30% |

**บทเรียนที่เขียนในธีสิสได้**: ทุกจุดที่ใช้ `-ErrorAction SilentlyContinue`
หรือ `try/except` ในเส้นทางเก็บข้อมูล **ต้องมี preflight ที่ throw คู่กันเสมอ**
ไม่งั้นได้ dataset ที่ดูปกติแต่ไม่มีสัญญาณที่ต้องการ
