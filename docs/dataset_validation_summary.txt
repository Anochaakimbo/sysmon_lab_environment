================================================================================
  2. วิธีติด Label และข้อจำกัดที่ยอมรับ
================================================================================

  label = 1  แปลว่า  "event นี้เกิดจาก process ที่สืบสายมาจากโฟลเดอร์ sandbox"
                     (/tmp/lab_sandbox บน Linux, C:\lab_sandbox บน Windows)

  ไม่ได้แปลว่า "event นี้มีลักษณะเป็นมัลแวร์ในตัวเอง"

  วิธีทำงาน (host/label_events.py)
      1. หา seed  = process ที่ Image หรือ CurrentDirectory อยู่ในโฟลเดอร์ sandbox
      2. แพร่ label ลงลูกหลานผ่าน ParentProcessGuid  วนจนไม่มีอะไรเพิ่ม
      3. ติด label ให้ทุก event ของ process ที่ติดธง
         (ไม่ใช่แค่ ProcessCreate แต่รวม FileCreate/NetworkConnect/RegistrySetValue)

  ทำไมไม่ใช้วิธี session (ทั้ง session = malicious)
      วัดแล้ว session mode ให้ malicious 100% ทั้งที่ lineage บอกแค่ 8.9%
      -> ใช้ lineage สำหรับ malicious เสมอ  ใช้ session แค่กับ benign

    DIRECT - ร่องรอยอยู่ในคอลัมน์ของ event นั้นเอง

    PARENT - ตัวมันไม่มีร่องรอย แต่ process แม่มี

        event         : ProcessTerminate
        Image         : C:\Windows\System32\conhost.exe
        CommandLine   : \??\C:\Windows\system32\conhost.exe 0xffffffff -ForceV1
        ParentCmdLine : "cmd.exe" /c schtasks /delete /tn "ATOMIC-T1053.005" /F

        conhost.exe เองไม่ได้ทำอะไร แต่ถูก spawn โดยคำสั่ง schtasks
        ที่เป็น T1053.005 จริง -> อ้างได้แบบมีเงื่อนไข


    OSBOOK - OS จดของมันเองเพราะ process เรารัน  ไม่ใช่พฤติกรรมมัลแวร์

        TargetObject   : HKLM\System\CurrentControlSet\Services\bam\State\
                         UserSettings\<SID>\...
        TargetFilename : C:\Users\vagrant\AppData\Local\Microsoft\Windows\
                         PowerShell\StartupProfileData

        BAM = Background Activity Moderator ระบบที่ Windows ใช้จดว่ามีโปรแกรม
        อะไรถูกรัน  มันจดเพราะ process ของเรารัน แต่การจดเป็นงานของ Windows
        -> ถ้านับรวมเป็นพฤติกรรมมัลแวร์คือการรายงานเกินจริง


    LINEAGE - ไม่มีหลักฐานทั้งในตัวเองและใน parent

        event         : ProcessTerminate
        Image         : C:\Windows\System32\conhost.exe
        TargetObject  : (ว่าง)
        ParentCmdLine : powershell.exe -c "write-host -Fore..."

    ประเด็นสำคัญ
      - RegistrySetValue มี DIRECT สูงสุด 70%  ซึ่งสอดคล้องกับเปเปอร์อ้างอิง
        ที่พบว่า event นี้แบก signal มากที่สุด (malicious 56.8% ในชุดของเขา)
        เป็นการยืนยันข้ามงานวิจัย
      - ProcessTerminate เป็น 33% ของ dataset แต่ DIRECT แค่ 26%

        ต่อให้เป็นมัลแวร์จริง event นี้ก็ไม่มีทางมีหลักฐานในตัว
      - FileCreate มี OSBOOK 17% (PowerShell startup profile, cache)
        จึงต้องรายงาน OSBOOK แยกจาก DIRECT

  ชั้นที่ 3 : เทียบกับ dataset ที่ตีพิมพ์แล้ว (NLME.csv)
  --------------------------------------------------------------------------

    เปเปอร์อ้างอิง : Achmad, Nariswari, Pratomo et al.
                     Cyber Security and Applications 3 (2025) 100110
    NLME.csv       : 71,017 แถว จาก 5 host (WKSTN-1 ถึง WKSTN-5)
                     รันมัลแวร์จริงจาก VirusShare
                     label benign 75.8% / malicious 24.2%

    วิธีวัด : "ระยะห่างองค์ประกอบ" = ผลรวมความต่างสัมบูรณ์ของสัดส่วน EventID
              เป็นจุดเปอร์เซ็นต์  (0 = เหมือนกันเป๊ะ, 200 = ไม่ทับกันเลย)
              เทียบเฉพาะแถว malicious เพราะ benign ของสองงานมาจากคนละสภาพแวดล้อม


    ขั้นแรก : แสดงว่า "องค์ประกอบเดียวของเปเปอร์" ไม่มีอยู่จริง

        host ของเปเปอร์          ระยะจากค่าเฉลี่ยของเปเปอร์เอง
        ---------------------    -----------------------------
        WKSTN-3                          41.3
        WKSTN-1                          41.7
        WKSTN-2                          55.1
        WKSTN-4                          58.6
        WKSTN-5                          67.7

        host ของเปเปอร์เองต่างกันสูงสุด  122.3 จุด
          WKSTN-2 : RegistrySetValue 72.7%  ProcessCreate 11.1%
          WKSTN-5 : RegistrySetValue 13.6%  ProcessCreate 59.2%

        -> การไล่ให้ตรงเป๊ะจึงไม่ใช่เป้าหมายที่มีความหมาย
           เกณฑ์ที่ยุติธรรมคือ "อยู่ในช่วงความแปรปรวนของเปเปอร์เอง"


    ขั้นที่สอง : ของเรา  ต้องเทียบแบบเทียบของชนิดเดียวกัน

        ชุดที่เทียบ                        ระยะ      แถว
        ------------------------------  --------  --------
        ทั้งหมด (Linux + Windows)           95.9    27,499
        ทั้งหมด ตัด event 9, 23              90.5    23,878
        เฉพาะ Windows                       75.3    11,993
        เฉพาะ Windows ตัด event 9, 23       57.3     9,711   <-- อยู่ในช่วง

        57.3 อยู่ในช่วง 41.3 - 67.7 ที่ host ของเปเปอร์เองต่างกัน

        เหตุผลที่ต้องตัด event 9 (RawAccessRead) และ 23 (FileDelete)
          เปเปอร์ไม่ได้เก็บสอง event นี้เลยสักแถว
          เราเปิดไว้เพื่อให้ merge กับ Linux ได้ (เป็น event ร่วมสองแพลตฟอร์ม)
          ตอนเทียบกับเปเปอร์จึงต้องกรองออก ไม่งั้นเทียบคนละของ

        เหตุผลที่ไม่ตัด ProcessTerminate ตามเปเปอร์
          เปเปอร์มี ProcessCreate 27.8% แต่ ProcessTerminate เพียง 6.2%
          ตรวจ EVTX ดิบจาก repo ของเขาแล้วพบอัตราส่วนเดียวกัน (14 : 1)
          -> ไม่ใช่การถูกตัดตอนทำ CSV แต่เป็นการตั้งค่าเก็บของเขาเอง
             ที่ไม่ได้เก็บ ProcessTerminate ครบ
             ตัดตามเขา = ลอกข้อจำกัดของเขามาด้วย  ของเราเก็บครบกว่า


    ข้อค้นพบเพิ่มเติมที่ใช้ปรับการเก็บให้ตรงเปเปอร์
        EventID 12 ของเปเปอร์ไม่มี CreateKey เลยสักแถว
        มีแต่ DeleteValue 1,126 + DeleteKey 20
        -> config ของเปเปอร์กรอง CreateKey ออก
        ของเราก่อนแก้ EventID 12 = CreateKey 20,332 จาก 20,356 (99.9%)
        เจ้าของคือ powershell.exe = registry churn ของ harness ไม่ใช่มัลแวร์
        -> เพิ่ม exclude CreateKey ใน sysmon config
           เป็นการทำให้ตรงเปเปอร์ ไม่ใช่แค่ลด noise  อ้างอิงได้ว่าวัดจาก NLME.csv

       -> ครอบคลุมพฤติกรรม C2 / beaconing ที่เปเปอร์ไม่ได้ครอบคลุม

    2. เปเปอร์ไม่มี FileDelete (23) และ RawAccessRead (9) เลย
       -> ยืนยันว่าการกรองสอง event นี้ออกตอนเทียบองค์ประกอบเป็นสิ่งที่ถูกต้อง

    3. เปเปอร์มี CreateRemoteThread 4,441 (6.3%) ส่วนเราแทบไม่มี
       -> เป็นช่องว่างจริงของงานเรา  process injection ของ ART สำเร็จน้อย

    4. เปเปอร์เก็บ Security log ไว้แต่ไม่ได้ใช้
       -> การรวม 4624 / 4648 เข้ากับ Sysmon เป็นทิศทางต่อยอดที่เขาเปิดช่องไว้

  ตรวจแล้ว - ยังเป็นข้อจำกัด ต้องจัดการในเฟส ML
  --------------------------------------------------------------------------
  [ข้อจำกัด] Platform leakage
         โมเดลทำนายว่าแถวนี้มาจาก Windows หรือ Linux ได้ 99.99%
         (ทายมั่วได้ 55.7%)
         feature ที่รั่วมากสุด : Image, IntegrityLevel, TerminalSessionId,
                                LogonId, User, CurrentDirectory
         หลังตัด 19 คอลัมน์ที่รั่ว เหลือ 70.65%  ลดได้แต่ไม่หมด
         -> ต้องเลือก feature หรือแยกเทรน  ห้าม merge แบบ union ตรงๆ

  [ข้อจำกัด] event type ที่มีอยู่ฝั่งเดียว
         EventID 2, 8, 12, 13 มีเฉพาะ Windows / EventID 4 มีเฉพาะ Linux
         RegistrySetValue 4,689 แถว เป็น event ที่แบก signal มากสุด
         ตัดทิ้ง = ทิ้งจุดแข็งฝั่ง Windows
         -> ควร map เป็น behavior concept ร่วม (CONFIG_CHANGE)
            โดยฝั่ง Linux ใช้การเขียนไฟล์ใน /etc/, cron, systemd

  [ข้อจำกัด] 59.2% ของแถว malicious ไม่มี artifact ในตัวเอง
         -> แก้ด้วยการ aggregate ขึ้นระดับ process / process-tree
            ตอนสร้าง feature  ไม่ใช้ 1 Sysmon row = 1 ML sample

  [ข้อจำกัด] การแบ่ง train / test
         ห้ามใช้ train_test_split แบบสุ่มแถว
         เพราะ event หลายแถวมาจาก process เดียวกัน สุ่มแล้วไปอยู่ทั้งสองฝั่ง
         โมเดลจะจำ process ได้แทนที่จะเรียนพฤติกรรม  ทำให้ F1 สูงเกินจริง
         -> ต้องใช้ GroupKFold โดย group = session หรือ ProcessGuid


================================================================================
  5. ข้อจำกัดที่ยอมรับตรงๆ (สำหรับสไลด์หน้าสุดท้าย)
================================================================================

  1. 59.2% ของแถว malicious ติด label จาก lineage ล้วน ไม่มี artifact ในตัวเอง

  2. 5.3% เป็น OSBOOK คือการที่ OS จดของมันเอง ไม่ใช่พฤติกรรมมัลแวร์
     รายงานแยกไว้แล้ว ไม่นับรวมเป็นหลักฐาน

  3. การ map artifact กลับไปหา technique ยังไม่แม่น 100%
     มีบางแถวที่คำสั่งของ harness เอง เช่น bash -c ... /tmp/lab_sandbox/...
     ถูกนับเป็น T1059.004

  4. ปิด Windows Defender ตอนเก็บข้อมูล
     เหตุผล : ถ้าไม่ปิด atomic test ที่โหลดไฟล์จะถูกบล็อกแบบเงียบ
              ทำให้ NetworkConnect ฝั่ง malicious เป็น 0 ทั้งที่ test รายงานว่าสำเร็จ
     ผลกระทบ : dataset ไม่สะท้อนเครื่องที่มี AV ทำงานอยู่

  5. ใช้ Atomic Red Team ซึ่งเป็นการจำลอง technique ไม่ใช่มัลแวร์ตัวจริง
     ต่างจากเปเปอร์อ้างอิงที่ใช้ VirusShare sample จริง
     ข้อดี  : map ATT&CK ได้ตรง ทำซ้ำได้ ระบุได้ว่าแต่ละ event มาจาก technique ใด
     ข้อเสีย: ไม่มีพฤติกรรมนอกเหนือจาก technique ที่เลือกไว้


================================================================================
  6. สรุปหนึ่งย่อหน้าสำหรับตอบกรรมการ
================================================================================

  เราไม่ได้พิสูจน์ด้วยการอ้างว่า label ถูกต้อง แต่พิสูจน์สามทาง

  หนึ่ง  ทุกกิจกรรมในแล็บ map กับ MITRE ATT&CK technique ได้
         เลข test ทุกตัวยืนยันกับ Atomic Red Team บนเครื่องจริงแล้ว

  สอง   32.0% ของแถว malicious มี artifact ยืนยันอยู่ในตัว event เอง
         เช่น Registry Run key, NetWire RAT key, systemd service,
         การ dump /etc/shadow  และเมื่อแยกตามชนิด event พบว่า
         RegistrySetValue ซึ่งเป็น event ที่แบก signal มากที่สุด
         มี artifact ยืนยันถึง 70%

  สาม   องค์ประกอบ event ของฝั่ง Windows ห่างจาก dataset ของเปเปอร์อ้างอิง
         57.3 จุด ซึ่งอยู่ในช่วง 41.3 ถึง 67.7 ที่ host ของเปเปอร์เองแตกต่างกัน

  ส่วนที่ยังพิสูจน์ไม่ได้ คือ 59.2% ที่ติด label จากสายเลือดล้วน
  เรารายงานตัวเลขนี้ตรงๆ และแก้ด้วยการรวมข้อมูลขึ้นเป็นระดับ process
  ตอนสร้าง feature ซึ่งทำให้ event ที่ไม่มีหลักฐานในตัวเอง
  ถูกรวมเข้ากับ process ที่มีหลักฐานยืนยัน
