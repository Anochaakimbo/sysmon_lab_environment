## 0. สรุปใน 30 วินาที

สร้างชุดข้อมูล Sysmon สำหรับตรวจจับมัลแวร์ **สองแพลตฟอร์ม (Linux + Windows)** โดยเก็บเองในแล็บด้วย Atomic Red Team
ติด label ตาม **สายโปรเซส (lineage)** แทนการติดทั้งช่วงเวลา แล้วรวม event เป็น **ฟีเจอร์ระดับโปรเซส 32 ตัว**
Random Forest ได้ **F1 0.925 / AUC 0.987** ด้วยการแบ่งข้อมูลที่ไม่รั่ว และวัดซ้ำในหลายเงื่อนไข ได้แก่ zero-day, รอบใหม่ และเครื่องใหม่
จากนั้นนำไปทดสอบกับชุดข้อมูลสาธารณะ 6 ชุด
ใช้ได้กับชุดที่เก็บ Sysmon ครบ (APT29 AUC 0.86, BarongTrace accuracy 0.757) และระบุข้อจำกัดไว้ตรงๆ
โดยเฉพาะการพึ่งความยาวคำสั่ง

ต่อยอดจาก Achmad et al., *Cyber Security and Applications* 3 (2025) 100110 ซึ่งทำเฉพาะ Windows
และระบุเองว่าข้อจำกัดคือไม่มีความสัมพันธ์ parent–child

## 1. สภาพแวดล้อมและท่อเก็บข้อมูล

| ส่วน | รายละเอียด |
|---|---|
| Host | Windows 11, Ryzen 7 9700X, RAM 32GB |
| Hypervisor | VMware Workstation + Vagrant (VirtualBox บูตไม่ผ่านเพราะ Hyper-V) |
| Linux VM | Ubuntu 22.04, Sysmon for Linux (schema 4.81) |
| Windows VM | Windows 10 + Sysmon + Atomic Red Team, ปิด Defender/Tamper Protection |
| Linux transport | Sysmon → journald → rsyslog → TCP 5514 → `log_receiver.py` |
| Windows transport | Sysmon Event Log → export XML ตอนจบรอบ |
| Pipeline | `parse_sysmon.py` (49 คอลัมน์) → `enrich_events.py` (54) → `label_events.py` (56) |
| ควบคุมรอบ | `orchestrator.py` / `orchestrator_win.py`: revert snapshot → boot → รัน scenario วนจนครบเวลา → halt → pipeline |
| Dashboard | กดเก็บผ่านเว็บได้ทั้งสองแพลตฟอร์ม และเปิด C2 / mining pool จำลองให้อัตโนมัติ |

รันทีละ VM เพราะ RAM ไม่พอรันพร้อมกัน

**เทคนิคที่ต้องรู้:**
- **Revert snapshot ก่อนทุกรอบ:** ทุกรอบเริ่มจากเครื่องสะอาด และไม่มี artifact ค้างข้ามรอบ
- **หลัง revert ต้อง restart rsyslog และ sysmon:** snapshot คืน memory state มาด้วย ทำให้ socket และ eBPF probe ค้างอยู่ในสภาพเก่า
- **Enrichment:** process ที่เกิดก่อน Sysmon เริ่มจะไม่มี CommandLine จึงเติมจาก ProcessCreate ของ process เดียวกัน ฝั่ง Linux เติมได้จาก 41.8% เป็น 90.2%
- **raw log คือแหล่งความจริง:** CSV สร้างใหม่ได้เสมอด้วย `rebuild_dataset.py` โดยไม่ต้องเก็บใหม่

## 2. สถานการณ์ (scenario)

6 สถานการณ์ต่อ OS ได้แก่ **benign, ransomware, miner, botnet, trojan, exploit**

| | Linux | Windows |
|---|---|---|
| วิธีโจมตี | Atomic Red Team + สคริปต์ชดเชย (ART มี test Linux น้อย) | Atomic Red Team ล้วน (ART-driven) |
| ตัวอย่าง technique | T1486, T1496, T1053.003, T1548.001, T1105 | T1486, T1496, T1071.001, T1547.001, T1055, T1548.002 |
| botnet / miner | beacon ไป `c2_server.py`, pool ใน `mining_pool.py` (ในแล็บ) | เหมือนกัน beacon 30/30 รอบ, pool 20/20 |

**ความปลอดภัย:**
- **ระบุเลข test เสมอ:** ไม่ระบุ = รันทุก test เช่น T1070.004 test 8 คือ Delete Filesystem

- **checker ตัด test อันตราย:** `check_atomics.ps1` อ่าน `supported_platforms` จาก YAML แล้วตัด DESTRUCTIVE, LOGKILL, REBOOT, GUIBLOCK
- **ไม่เขียน payload มัลแวร์เอง:** botnet beacon แบบส่งอย่างเดียว ไม่รับคำสั่งกลับมารัน
- **ทุกอย่างอยู่ใน sandbox:** `/tmp/lab_sandbox` และ `C:\lab_sandbox`

## 3. การจัดการ dataset

### 3.1 การติด label: lineage
1. seed = โปรเซสที่รันจาก sandbox directory
2. ไล่ `ParentProcessGuid` ลงไปหาลูกหลานทั้งหมด
3. ทุก event ของโปรเซสในสาย = label 1 นอกนั้น = 0 (รอบ benign = 0 ทั้งหมด)

ทำไมไม่ติดทั้ง session: session mode ให้ malicious **100%** ส่วน lineage ให้ **8.9%**
เพราะ daemon ของ OS ที่ทำงานช่วงเดียวกันก็จะได้ label มัลแวร์ไปด้วย

### 3.2 การกรองและแก้ข้อมูล

| ทำอะไร | เหตุผล |
|---|---|
| กรอง registry ของ OS housekeeping (svchost, CompatTelRunner, EdgeUpdate ฯลฯ) ด้วย path เต็ม | RegistryEvent เดิมคิดเป็น 91% ของ event (118,796 → 23,018) ส่วน ProcessCreate มีแค่ 0.3% |
| กรอง CreateKey ใน EventID 12 | เปเปอร์ไม่มี CreateKey เลย (ตรวจจาก NLME.csv) ของเรามี 99.9% มาจาก PowerShell เอง |
| ตัด EventID 255 | เป็นข้อความ error ของ Sysmon เอง ไม่ใช่ telemetry |
| ใช้ `condition="is"` path เต็ม ไม่ใช้ชื่อไฟล์ | T1036.003 ปลอม powershell เป็น `taskhostw.exe`/`lsass.exe` ถ้ากรองตามชื่อจะกลืน telemetry ของ test เอง |
| composite key = platform \| run_id \| ProcessGuid | กัน GUID ซ้ำข้ามรอบ/เครื่อง |
| คอลัมน์ `run_id` | คอลัมน์ `session` เก็บแค่ชื่อ scenario ถ้าไม่มี run_id จะแยกรอบไม่ได้ |

### 3.3 บั๊กที่เจอเองและแก้แล้ว (silent failure ทั้งหมด: exit 0 แต่ข้อมูลผิด)

| อาการ | สาเหตุ | แก้ |
|---|---|---|
| trojan_win ได้ CSV 18,072 แถว ดูปกติ แต่ไม่มี atomic ทำงานเลย | ART module import ไม่ติด แล้ว `-ErrorAction SilentlyContinue` กลืน error | import ตาม path เต็ม และ preflight ที่ throw |
| NetworkConnect malicious = 0 | Defender (AMSI) บล็อกคำสั่งดาวน์โหลด และ Tamper Protection ย้อนการตั้งค่าเงียบๆ | ปิด Tamper Protection ด้วย GUI แล้ว `Assert-DefenderOff` |
| FileCreate หายทั้งรอบบน Linux | eBPF probe ค้างหลัง revert | `systemctl restart sysmon` |
| Windows benign มีแค่ 528 แถว เทียบ Linux 5,330 | orchestrator_win รัน scenario ครั้งเดียว | เพิ่ม repeat loop ได้ 9,293 แถว (18 รอบ) |
| exploit_win ได้แค่ 1 รอบ | T1218.011 test 13 เปิด Control Panel แล้วค้างรอผู้ใช้ | ตัด test ออก และเพิ่ม tag GUIBLOCK |
| **สัดส่วน label Windows ผิด** (เจอหลังรีวิว) | parser อ่าน XML ทีละบรรทัด CommandLine หลายบรรทัดทำให้ 105 ProcessCreate เสีย ParentProcessGuid | ต่อบรรทัดจนเจอ `</Event>` Windows malicious 33.3% → **51.9%** แล้วคำนวณทุกตารางใหม่ ข้อสรุปไม่เปลี่ยน |
| Linux: คำสั่งที่ ART รันได้ label 0 | pwsh fork ก่อน exec แต่ Sysmon for Linux ไม่บันทึกตัวกลาง สายจึงขาด | **ยังไม่แก้** เขียนเป็นข้อจำกัด: ≈31% ของโปรเซสโจมตี |

## 5. การเลือกฟีเจอร์

### 5.1 ทำไมต้องระดับโปรเซส
event เดี่ยวของมัลแวร์หน้าตาเหมือนปกติ เช่น `powershell.exe` เขียนไฟล์ 1 ไฟล์
สิ่งที่แยกได้คือรูปแบบรวม เช่นเขียน 400 ไฟล์ใน 3 วินาที หรือต่อ IP เดิม 30 รอบ
ตัวเลขยืนยัน: RF F1 ระดับ event 0.811 เทียบระดับโปรเซส 0.959 (ข้อมูลรอบแรก)

### 5.2 ฟีเจอร์ 32 ตัว (`revised_experiments.aggregate`)

| กลุ่ม | ฟีเจอร์ | จำนวน |
|---|---|---|
| ปริมาณ | `n_events` | 1 |
| นับต่อชนิด event | `ev_1, ev_2, ev_3, ev_4, ev_5, ev_8, ev_9, ev_11, ev_12, ev_13, ev_23` | 11 |
| สัดส่วนต่อชนิด | `frac_*` ของ 11 ชนิดเดียวกัน | 11 |
| ความหลากหลายของเป้าหมาย | `n_files, n_dst_ip, n_dst_port, n_regobj, n_device` | 5 |
| เวลา | `dur_s, rate` | 2 |
| คำสั่ง | `cmd_len, pcmd_len` | 2 |

### 5.3 ฟีเจอร์ที่ตัดออก และเหตุผล

| ฟีเจอร์ | ทำไมตัด |
|---|---|
| `Image` / `img_len` | เปเปอร์ตัดเองเพราะ "direct association with the target variable" |
| `CurrentDirectory` | `C:\lab_sandbox\` = malicious 99.9% เพราะเป็นตัวเดียวกับที่ labeler ใช้ตัดสิน |
| `depth` / `ancestor_depth` | มาจาก lineage tree เดียวกับที่สร้าง label |
| `enriched`, `parent_known` | บอกว่าโปรเซสเกิดก่อนหรือหลัง Sysmon เป็นผลของ pipeline ไม่ใช่พฤติกรรม |
| ProcessGuid, UtcTime, host, session, record_id | เป็นตัวระบุ ไม่ใช่ฟีเจอร์ |

### 5.4 สิ่งที่ลองแล้วไม่ใช้
- **PCA ตามเปเปอร์:** sweep n=1..30 แล้ว n ที่ดีที่สุดเกือบเท่าจำนวนฟีเจอร์ทั้งหมด และที่ระดับ event ทำให้แย่ลง (F1 0.951 → 0.936) จึงไม่ใช้
- **encoder ของเปเปอร์** (label encoding / ความยาวสตริง): ยังแยก platform ได้ 100% จึงใช้ตรงๆ ไม่ได้

### 5.5 ชุดฟีเจอร์ทางเลือก (หลังรีวิว)
- **clean (53 ตัว):** 32 ตัว + ฟีเจอร์พฤติกรรม 21 ตัว และตัดโปรเซสของตัวรันทดสอบ (ART engine, conhost) ออกตอนฝึก
  - ฟีเจอร์พฤติกรรม ได้แก่ แตะไฟล์อ่อนไหว (`/etc/shadow`, Run key), entropy ชื่อไฟล์, จำนวนนามสกุลไฟล์, ต่อออกนอกเครือข่าย, สร้างแล้วลบไฟล์, จำนวนลูก, pipe/redirect, URL, IP literal, base64, รันจาก path ที่เขียนได้, พฤติกรรมของพี่น้อง (beacon period)
- **neutral (29 ตัว):** ตัดความยาวคำสั่งและฟีเจอร์ที่ผูกกับ OS ออก

## 9. คำถามที่น่าจะโดน และคำตอบ

### เรื่องข้อมูล
**Q1. ทำไมไม่ใช้มัลแวร์จริง**
มัลแวร์จริงต้องใช้เครือข่ายแยกและมีความเสี่ยงหลุดออกนอกแล็บ Atomic Red Team map กับ ATT&CK ตรงและทำซ้ำได้
แต่ยอมรับว่าเป็นข้อจำกัด จึงไปทดสอบกับ BarongTrace ซึ่งเป็นมัลแวร์จริงจาก VirusShare ได้ accuracy 0.757 เมื่อตั้งเกณฑ์จากข้อมูลปกติ

**Q2. 81,331 event พอไหม**
ระดับโปรเซสมี 23,971 ตัว และหลังรีวิวเก็บเพิ่มรวมเป็น 50 run ราว 480,000 event
การเพิ่มรอบเดิมแทบไม่เปลี่ยนผล (F1 0.911–0.953) สิ่งที่ขาดคือความหลากหลาย ไม่ใช่ปริมาณ

**Q2b. ทำไมไม่เทรนด้วยทั้ง 50 run ตั้งแต่แรก / เทรนแล้วดีขึ้นไหม**
โมเดลในเว็บเทรนด้วย 50 run แล้ว ผลนอกแล็บแทบไม่เปลี่ยน: APT29 AUC 0.832 → 0.858, BarongTrace AUC 0.774 → 0.756
เพราะส่วนที่เพิ่มส่วนใหญ่เป็นรอบซ้ำบนเครื่องเดิม ยืนยันว่าสิ่งที่ขาดคือความหลากหลาย ไม่ใช่ปริมาณ
ส่วนเปเปอร์ใช้ 12 run เพราะชุดอื่นเก็บหลังรีวิวเพื่อใช้ทดสอบ

**Q3. label 1 แปลว่าเป็นมัลแวร์จริงไหม**
แปลว่าสืบสายจาก sandbox ได้แยกหลักฐานเป็น 4 ระดับ (trojan_win):
- DIRECT 45.5% คือ artifact อยู่ใน event เอง
- PARENT 15.0% คือคำสั่งของ test อยู่ใน ParentCommandLine
- OSBOOK 16.8% คือ OS จดของมันเอง ไม่ใช่พฤติกรรมมัลแวร์
- LINEAGE 22.6% คือติด label เพราะสายเลือดล้วนๆ

**Q4. ปิด Defender แล้วไม่สมจริงหรือ**
ถ้าเปิด Defender จะบล็อก test ที่ดาวน์โหลดไฟล์ ทำให้ NetworkConnect malicious เป็น 0 จาก 77 แถว
ข้อมูลจะไม่มีพฤติกรรมให้เรียน จึงปิดและบันทึกไว้เป็นเงื่อนไขการเก็บ

**Q5. benign สมจริงแค่ไหน**
เป็นสคริปต์ที่สร้างโปรเซสใหม่จำนวนมาก (กันไม่ให้โมเดลเรียนว่า "ไม่มี CommandLine = ปกติ") แต่ยังเป็นคำสั่งสั้น
ซึ่งเป็นต้นเหตุของทางลัดความยาวคำสั่ง จึงเขียนเป็นงานต่อยอด

**Q6. บั๊ก parser ที่เจอหลังรีวิวกระทบผลไหม**
กระทบ label ฝั่ง Windows (33.3% → 51.9%) จึงคำนวณทุกตารางใหม่ด้วยโค้ดประเมินรุ่นเดิม
RF F1 เปลี่ยนจาก 0.920 เป็น 0.925 ข้อสรุปทุกข้อเหมือนเดิม

### เรื่องฟีเจอร์และโมเดล
**Q7. ทำไมเลือก 32 ฟีเจอร์นี้**
เป็นสิ่งที่ Sysmon ให้ทั้งสอง OS และสรุปพฤติกรรมระดับโปรเซสได้ ได้แก่จำนวนและชนิด event, ความหลากหลายของเป้าหมาย และเวลา
ฟีเจอร์ที่รั่ว label (CurrentDirectory, depth, Image) ตัดออกพร้อมหลักฐาน

**Q8. ทำไมไม่ทำ PCA ตามเปเปอร์**
ลองแล้ว n ที่ดีที่สุดเกือบเท่าจำนวนฟีเจอร์ทั้งหมด และที่ระดับ event ทำให้แย่ลง
เพราะฟีเจอร์ไม่มีความสัมพันธ์เชิงเส้นให้รวบ

**Q9. ทำไม Random Forest ดีที่สุด**
ฟีเจอร์เป็นนับจำนวนและสัดส่วนที่มี threshold ชัด ต้นไม้จับได้ดีและทนต่อสเกลต่างกัน
NB สมมติว่าฟีเจอร์อิสระกันจึง flag แทบทุกตัว (recall 0.977, FPR 0.948)

**Q10. ทำไม unsupervised ฝึกด้วย benign อย่างเดียว**
ตามเปเปอร์ Fig. 4 ถ้าฝึกด้วยข้อมูลผสม โมเดลจะนับพฤติกรรมมัลแวร์เป็นปกติ วัดแล้ว Isolation Forest ได้ AUC 0.44

**Q11. F1 0.925 สูงเกินจริงไหม**
แบ่งตามสายโปรเซส ไม่สุ่มแถว และรายงานผลที่เข้มกว่าคู่กันด้วย ได้แก่ zero-day 0.770 และข้ามเครื่อง 0.627–0.955
ทางลัดความยาวคำสั่งเป็นสิ่งที่พูดเองในสไลด์ 10

**Q12. ตัดความยาวคำสั่งแล้วเหลือ 0.602 แปลว่าโมเดลไม่ได้เรียนพฤติกรรมหรือ**
ส่วนหนึ่งใช่ แต่ชุด clean ที่ตัดโปรเซสของตัวรันทดสอบและเพิ่มฟีเจอร์พฤติกรรม ข้ามเครื่องได้ 0.835–0.977
และใช้กับ APT29 ได้ AUC 0.86 ทางแก้ที่ถูกคือทำ benign ให้มีคำสั่งยาว ไม่ใช่ตัด CommandLine ทิ้ง เพราะเป็น contribution

**Q13. รวมสอง OS ในโมเดลเดียวได้ไหม**
โมเดลแยก OS ได้เกือบ 100% จาก missing pattern และข้าม OS ได้ AUC 0.35–0.58 จึงฝึกแยก
แต่ใช้ pipeline และฟีเจอร์ชุดเดียวกันทั้งสองฝั่ง

**Q14. zero-day ทำได้ไหม**
leave-one-scenario-out ได้ RF F1 0.770 AUC 0.906 ตรวจการโจมตีที่ไม่เคยเห็นได้บางส่วน
แต่ไม่ใช่ zero-day จริง เพราะยังเป็น ART ชุดเดียวกัน

### เรื่องชุดข้อมูลสาธารณะ
**Q15. ทำไมได้ไม่ถึง 80% ทุกชุด**
ชุดภายนอกต่างจากแล็บทั้ง config ของ Sysmon, คอลัมน์ที่มี และนิยาม label
ชุดที่เก็บ Sysmon ครบได้ 73–76% (balanced accuracy) ส่วนชุดที่กรองหรือขาดคอลัมน์ใช้ไม่ได้ ซึ่งเป็นข้อค้นพบที่มีประโยชน์เอง

**Q16. APT29 accuracy 0.796 ต่ำกว่าทายว่าปกติทั้งหมด (0.933) ไม่แปลว่าแย่หรือ**
ชุดนั้นมีการโจมตีแค่ 6.7% การทายว่าปกติทั้งหมดจะได้ accuracy สูงแต่ตรวจจับได้ 0
AUC 0.86 กับ recall 0.72 ที่ FPR 0.20 คือตัวที่บอกความสามารถจริง

**Q17. label ของ APT29 ติดเองเชื่อถือได้ไหม**
ใช้จุดเริ่มตามแผนการโจมตีที่ MITRE เผยแพร่ (เช่น `cod.3aka3.scr`, PsExec, `.lnk`) แล้วไล่ lineage แบบเดียวกับแล็บ
ข้อจำกัดคือถ้าจับรากไม่ครบ ตัวที่ตกหล่นจะอยู่ฝั่งปกติ ผลจริงจึงอาจดีกว่าที่รายงาน

**Q18. การตั้งเกณฑ์จากข้อมูลปกติถือว่าโกงไหม**
ไม่ใช้ label การโจมตีเลย ใช้เฉพาะข้อมูลปกติของสภาพแวดล้อมปลายทาง ซึ่งในการติดตั้งจริงหาได้ตอนเริ่มเฝ้าระวัง
และทดสอบบนไฟล์/host ที่ไม่ได้ใช้ตั้งเกณฑ์ ถ้าไม่ตั้งเกณฑ์ BarongTrace ได้ accuracy 0.609

**Q19. ทำไมต้องปิดชื่อไฟล์ BarongTrace**
มัลแวร์ชื่อ `VirusShare_<md5>` ยาว 43 ตัว ส่วน benign ชื่อเครื่องมือสั้นๆ ความยาวคำสั่งจึงบอกคำตอบ
ถ้าไม่ปิดจะได้ตัวเลขสูงปลอม
