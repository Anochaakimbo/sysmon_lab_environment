## กลุ่ม A — Cross-platform generalization (Reviewer 1 ข้อ 1)

### ข้อความใหม่: หัวข้อ 4.4 (ต่อท้ายหัวข้อ 4.3)

**4.4 ผลเมื่อฝึกจากระบบปฏิบัติการหนึ่งและทดสอบกับอีกระบบหนึ่ง**

เพื่อตรวจว่าแบบจำลองที่ฝึกจากระบบปฏิบัติการหนึ่งนำไปใช้กับอีกระบบหนึ่งได้หรือไม่ ผู้วิจัยฝึก Random Forest
ด้วยตัวอย่างทั้งหมดของระบบปฏิบัติการหนึ่ง แล้วทดสอบกับตัวอย่างทั้งหมดของอีกระบบหนึ่ง และเทียบกับการฝึกและทดสอบ
ภายในระบบปฏิบัติการเดียวกันด้วยการแบ่งตามสายโปรเซส 5 fold ผลแสดงในตาราง 5

ตาราง 5 ผลของ Random Forest เมื่อฝึกและทดสอบต่างระบบปฏิบัติการ (ฟีเจอร์ 32 ตัว)

| ฝึก → ทดสอบ | F1 | ROC-AUC | F1 ของการทำนาย label=1 ทุกตัวอย่าง |
|---|---|---|---|
| Linux → Linux | 0.912 | 0.986 | 0.469 |
| Windows → Windows | 0.971 | 0.996 | 0.637 |
| Linux → Windows | 0.102 | 0.581 | 0.637 |
| Windows → Linux | 0.419 | 0.351 | 0.469 |

เมื่อฝึกและทดสอบภายในระบบปฏิบัติการเดียวกัน ROC-AUC สูงกว่า 0.98 ทั้งสองระบบ แต่เมื่อฝึกจาก Linux แล้วทดสอบกับ
Windows ROC-AUC ลดเหลือ 0.581 และเมื่อฝึกจาก Windows แล้วทดสอบกับ Linux ได้ 0.351 ซึ่งต่ำกว่าการทายสุ่ม (0.5)
และ F1 ทั้งสองทิศต่ำกว่าการทำนายทุกตัวอย่างเป็น label=1 ผลนี้สอดคล้องกับ [10] ที่พบว่าประสิทธิภาพลดลงมากเมื่อใช้
แบบจำลองข้ามระบบปฏิบัติการ สาเหตุหนึ่งคือฟีเจอร์ขึ้นกับระบบปฏิบัติการ เช่น ความยาวคำสั่งต่างกันตามรูปแบบ path
และชนิดเหตุการณ์รีจิสทรีมีเฉพาะ Windows อีกสาเหตุคือสถานการณ์ของสองระบบใช้เทคนิคและคำสั่งต่างกัน (ตาราง 1)
ดังนั้นผลในตาราง 3 และ 4 ซึ่งฝึกด้วยข้อมูลทั้งสองระบบร่วมกัน จึงไม่ได้แสดงว่าความรู้ถ่ายทอดข้ามระบบปฏิบัติการได้
ชุดข้อมูลและขั้นตอนเตรียมข้อมูลใช้ร่วมกันได้ แต่ควรฝึกแบบจำลองแยกต่อระบบปฏิบัติการ

### แก้บทนำ (ย่อหน้าผลงานหลัก)

เพิ่มท้ายประโยค: "…และผลเปรียบเทียบเมื่อแบ่งข้อมูลตามสายโปรเซส รอบทดลอง ประเภทการโจมตี **และระบบปฏิบัติการ**"

### แก้บทสรุป

เพิ่ม: "เมื่อฝึกจากระบบปฏิบัติการหนึ่งแล้วทดสอบกับอีกระบบหนึ่ง ROC-AUC ลดเหลือ 0.351–0.581 แบบจำลองจึงควรฝึกแยกต่อระบบปฏิบัติการ"

### ตอบ reviewer

> ขอบคุณสำหรับข้อเสนอแนะ ผู้วิจัยเพิ่มการทดลองฝึกจาก Linux ทดสอบกับ Windows และฝึกจาก Windows ทดสอบกับ Linux
> ในหัวข้อ 4.4 และตาราง 5 พบว่า ROC-AUC ลดจากมากกว่า 0.98 ภายในระบบปฏิบัติการเดียวกัน เหลือ 0.581 และ 0.351
> ตามลำดับ สอดคล้องกับ [10] ผู้วิจัยจึงปรับข้อสรุปว่า contribution ด้านข้ามแพลตฟอร์มคือชุดข้อมูลและขั้นตอน
> เตรียมข้อมูลที่ใช้ร่วมกันได้ โดยแบบจำลองควรฝึกแยกต่อระบบปฏิบัติการ

## กลุ่ม B — การพึ่งพา cmd_len / shortcut feature (Reviewer #21B ข้อ 2, Reviewer 1 ย่อหน้าสรุป)

### ข้อความใหม่: แทนย่อหน้าแรกของหัวข้อ 5 ส่วนที่พูดถึง cmd_len

เพื่อตรวจการพึ่งพาฟีเจอร์ ผู้วิจัยวัดความสำคัญของฟีเจอร์ของ Random Forest สองแบบ แบบแรกคือ impurity-based importance
แบบที่สองคือ permutation importance ซึ่งวัดว่า F1 ลดลงเท่าใดเมื่อสลับค่าฟีเจอร์นั้นในชุดทดสอบ (ตาราง 6)

ตาราง 6 ฟีเจอร์ที่สำคัญที่สุด 5 อันดับของ Random Forest (fold แรกของการแบ่งตามสายโปรเซส)

| ฟีเจอร์ | Impurity importance | F1 ที่ลดลงเมื่อสลับค่า |
|---|---|---|
| pcmd_len | 0.287 | 0.265 |
| cmd_len | 0.290 | 0.224 |
| dur_s | 0.174 | 0.116 |
| rate | 0.067 | 0.041 |
| ev_23 | 0.021 | 0.007 |

ความยาวคำสั่งสองตัวรวมกันมีความสำคัญราว 0.58 ของทั้งหมด และเมื่อตัดออก F1 ลดจาก 0.925±0.012 เป็น 0.602±0.042
ROC-AUC ลดจาก 0.987 เป็น 0.795 ค่ามัธยฐานของ cmd_len คือ 25 ตัวอักษรสำหรับ label=0 และ 42 ตัวอักษรสำหรับ label=1
ความต่างนี้อาจมาจากรูปแบบคำสั่งของชุดทดสอบ Atomic Red Team ซึ่งเรียกคำสั่งผ่านตัวกลาง เช่น
`"powershell.exe" & {...}` และพฤติกรรมปกติในการทดลองเป็นคำสั่งสั้นที่สร้างจากสคริปต์ ความยาวคำสั่งจึงอาจเป็น
shortcut feature ของชุดข้อมูลจำลอง มากกว่าเป็นลักษณะของการโจมตีโดยทั่วไป

ฟีเจอร์ที่สำคัญรองลงมาคือ dur_s และ rate ซึ่งสะท้อนระยะเวลาและอัตราการเกิดเหตุการณ์ของโปรเซส ส่วนฟีเจอร์
ด้านไฟล์และเครือข่ายมีความสำคัญต่ำ ผลนี้ชี้ว่าฟีเจอร์ 32 ตัวยังจับพฤติกรรมเชิงไฟล์และเครือข่ายได้ไม่มาก
งานในอนาคตควรเพิ่มฟีเจอร์พฤติกรรม เช่น การเข้าถึง path ที่อ่อนไหว จำนวนไฟล์ที่สร้างแล้วลบ และการเชื่อมต่อออกนอก
เครือข่าย และใช้พฤติกรรมปกติที่มีคำสั่งยาวหลากหลาย เพื่อลดการพึ่งพาความยาวคำสั่ง

### (ทางเลือก) ผลเพิ่มเติมจากชุดฟีเจอร์พฤติกรรม

ใส่ได้ถ้าหน้ายังพอ ต้องระบุเงื่อนไขชัดเจน:
"ในการวิเคราะห์เพิ่มเติม เมื่อตัดโปรเซสของเครื่องมือทดสอบออก และใช้ฟีเจอร์พฤติกรรม 38 ตัวที่ไม่มีความยาวคำสั่ง
แบบจำลองที่ฝึกและทดสอบภายในระบบปฏิบัติการเดียวกันได้ ROC-AUC 0.997 (Linux) และ 0.997 (Windows)
แสดงว่าข้อมูลมีสัญญาณด้านพฤติกรรมที่ใช้แทนความยาวคำสั่งได้ แต่ยังต้องยืนยันด้วยการแยกรอบทดลอง"
⚠️ ชุดนี้มีจำนวนตัวอย่างต่างจากตาราง 3 เพราะตัดโปรเซสของเครื่องมือทดสอบออก

### ตอบ reviewer

> ขอบคุณสำหรับข้อเสนอแนะ ผู้วิจัยเพิ่ม feature importance ทั้งแบบ impurity และ permutation (ตาราง 6) พบว่า
> pcmd_len และ cmd_len เป็นสองอันดับแรก และอภิปรายในหัวข้อ 5 ว่าความยาวคำสั่งน่าจะเป็น shortcut จากรูปแบบคำสั่ง
> ของชุดทดสอบและพฤติกรรมปกติที่สร้างจากสคริปต์ (มัธยฐาน 25 เทียบกับ 42 ตัวอักษร) พร้อมเสนอแนวทางลดการพึ่งพา
> ฟีเจอร์นี้ในงานต่อไป

## กลุ่ม C — จำนวนรอบและความหลากหลายของสภาพแวดล้อม

(ร่างไว้แล้วในแชท — วางต่อท้ายข้อจำกัดในหัวข้อ 5)

> ข้อจำกัดด้านความหลากหลายของข้อมูล: ชุดข้อมูลหลักเก็บจากเครื่องเสมือนเพียงหนึ่งเครื่องต่อระบบปฏิบัติการ ใช้ไฟล์
> ตั้งค่าและรุ่น Sysmon เดียว และมีข้อมูลเพียงหนึ่งรอบต่อสถานการณ์ต่อระบบปฏิบัติการ ส่วนรอบทดลองใหม่มี 2 รอบบน
> Linux เท่านั้น คำสั่งโจมตีมาจาก Atomic Red Team และสคริปต์ที่ผู้วิจัยเขียน ส่วนพฤติกรรมปกติเป็นสคริปต์ที่สร้างขึ้น
> และเก็บข้อมูลขณะปิด Defender แบบจำลองจึงอาจเรียนรู้ลักษณะเฉพาะของสภาพแวดล้อมหรือรูปแบบคำสั่งในการทดลอง
> มากกว่าพฤติกรรมการโจมตีโดยทั่วไป ผลในตาราง 4 สะท้อนความเสี่ยงนี้ โดย F1 ลดจาก 0.925 เป็น 0.755±0.177
> เมื่อแยกรอบทดลอง งานในอนาคตควรเก็บซ้ำหลายรอบ หลายเครื่อง หลายรุ่นของระบบปฏิบัติการและ Sysmon และใช้
> รูปแบบคำสั่งหลายแบบทั้งในพฤติกรรมปกติและการโจมตี

### ข้อจำกัดเรื่องรูปแบบคำสั่ง (Reviewer #21B ข้อ 1, command variants) — ไม่ได้ทำเพิ่ม เขียนเป็นข้อจำกัด

> ทุกรอบและทุกเครื่องใช้ชุดทดสอบ Atomic Red Team และสคริปต์พฤติกรรมปกติชุดเดียวกัน คำสั่งโจมตีจึงมีรูปแบบเดียว
> ต่อเทคนิค และพฤติกรรมปกติส่วนใหญ่เป็นคำสั่งสั้น ผลข้ามเครื่องจึงวัดความทนต่อการเปลี่ยนเครื่องและรุ่นระบบปฏิบัติการ
> แต่ยังไม่ได้วัดความทนต่อการเปลี่ยนรูปแบบคำสั่งของการโจมตีเดียวกัน (เช่น obfuscation หรือเครื่องมือคนละตัว)
> ซึ่งสัมพันธ์กับการพึ่งพาความยาวคำสั่งในตาราง 6 งานในอนาคตควรสร้างรูปแบบคำสั่งหลายแบบต่อเทคนิค
> และพฤติกรรมปกติที่มีคำสั่งยาวหลากหลาย

### (ทางเลือก) การทดลองเพิ่มหลังรีวิว: เครื่องที่สอง รุ่น OS ต่างกัน

เก็บสถานการณ์เดิมทั้ง 6 (benign + 5 การโจมตี) บนเครื่องใหม่ระบบละหนึ่งเครื่อง คนละรุ่นกับชุดหลัก
Ubuntu 24.04 (kernel 6.8) และ Windows 11 สคริปต์ ไฟล์ตั้งค่า Sysmon และวิธีติด label เหมือนเดิมทุกอย่าง
แล้วทดสอบแบบ leave-one-machine-out: เทรนบนเครื่องหนึ่ง ทดสอบอีกเครื่อง (ระบบปฏิบัติการเดียวกัน)
รายงานแยกจากตาราง 3–4 ไม่ได้รวมเข้าชุดข้อมูลหลัก (`host/machine_eval.py`, ข้อมูล `data/machine2/`)

| ข้อมูล | Linux | Windows |
|---|---|---|
| เครื่อง 1 (ชุดหลัก) | Ubuntu 22.04, 45,311 event, malicious 34.2% | Windows 10, 36,020 event, 51.9% (label แก้แล้ว) |
| เครื่อง 2 (หลังรีวิว) | Ubuntu 24.04, 50,329 event, 40.0% | Windows 11, 68,996 event, 35.7% |

Random Forest เกณฑ์ 0.5, process-level, F1 / AUC (เทรน → ทดสอบ), Windows ทั้งสองเครื่องใช้ label จาก parser ที่แก้แล้ว:

baseline ทาย malicious ทุกตัว F1 0.39–0.66

> ข้อความที่วางได้: เพื่อประเมินผลของสภาพแวดล้อม ผู้วิจัยเก็บข้อมูลสถานการณ์เดิมเพิ่มบนเครื่องที่สองที่ใช้รุ่นระบบ
> ปฏิบัติการต่างกัน (Ubuntu 24.04 และ Windows 11) แล้วเทรนบนเครื่องหนึ่งและทดสอบบนอีกเครื่อง ด้วยฟีเจอร์ 32 ตัว
> ของบทความ F1 ลดจาก 0.912 เป็น 0.740 บน Linux และจาก 0.971 เป็น 0.955 บน Windows และเมื่อเทรนบนเครื่องใหม่
> แล้วทดสอบเครื่องเดิมได้ 0.627 และ 0.838 เมื่อตัดกระบวนการของเครื่องมือทดลองออกและใช้ฟีเจอร์พฤติกรรม
> F1 ข้ามเครื่องเป็น 0.835–0.977 แสดงว่าความแม่นยำส่วนหนึ่งผูกกับเครื่องที่เก็บข้อมูล
> และฟีเจอร์เชิงพฤติกรรมย้ายข้ามเครื่องได้ดีกว่า

ข้อควรระวังในการเขียน:
- เป็นสถานการณ์เดิมบนเครื่องใหม่ ไม่ใช่การโจมตีที่ไม่เคยเห็น และยังใช้ ART ชุดเดิม
