## 4. ระบบแจ้งเตือนสด (ตอบคำถาม "ป้องกันได้ไหม")

ทำเป็น **detect + alert** (EDR แบบเบา) ไม่ใช่ prevention — การบล็อกก่อนรันต้องใช้ kernel hook ซึ่งเกินขอบเขต

| ส่วน | ไฟล์ |
|---|---|
| ทดสอบย้อนหลังจาก log (time-to-detect, false alarm/ชม., learning curve ของ benign) | `host/replay_detect.py` |
| ตัวตรวจจับสด (tail log, ทุก 5 วินาที, แจ้งเตือนต่อเครื่องต่อช่วงเวลา) | `host/live_detector.py` |
| ส่ง Sysmon ของ Windows VM ไป host แบบสด | `scenarios_win/stream_sysmon.ps1` |
| ปุ่ม **Live demo — Windows** + แผง **Alerts** | `host/dashboard.py` |

แต่ละ alert มี: ระดับความรุนแรง (discovery อย่างเดียว = LOW, transfer/staging/persistence = HIGH, ≥3 technique ใน window = HIGH), ATT&CK technique, หลักฐาน (ไฟล์/registry/คำสั่งที่เกิดจริง), lineage

**ทดสอบบน Windows VM จริง (โมเดลไม่เคยเห็น trojan):** event → alert ประมาณ 4–5 วินาที
- alert #1 **LOW** — `Get-Process` (T1057 discovery)
- alert #2 **HIGH** — `Compress-Archive` → `Folder_to_zip.zip` (T1074.001 staging)

ข้อควรระวังตอน demo: เครื่อง host เปิด **Smart App Control** ซึ่งเคยบล็อก DLL ของ scipy เป็นบางครั้ง → dashboard จะขึ้น error ชัดเจนแล้วกดรันใหม่ได้ ควรซ้อมก่อน demo 1 รอบ

## 6. ข้อจำกัด

- Linux zero-day ยังอ่อนกว่า Windows: scenario ฝั่ง Linux ใช้คำสั่งปกติ (openssl, rm, curl) แยกจากงานแอดมินยาก; anomaly detector (LOF) ช่วยไม่ได้
- คำสั่ง discovery ที่เหมือนกันทุกตัวอักษร (`whoami`, `tasklist`, `hostname`) ระหว่าง benign กับ ART แยกจากตัว process ไม่ได้ — `benign.ps1` เดิมถูก flag 66% ที่ threshold FPR 5% → จึงให้ discovery เป็น LOW
- feature จังหวะ beacon ไม่ช่วย เพราะ benign ที่เป็นสคริปต์ก็สม่ำเสมอพอกัน (ข้อจำกัดของ benign สังเคราะห์)
- false alarm/ชม. วัดจาก benign ราว 0.5 ชม. ต่อ OS — 1 alert ≈ 2 FA/ชม.
- ทุกอย่างเป็น simulated attack (ART + สคริปต์ในแล็บ) ไม่ใช่มัลแวร์จริง

### 6.1 Lineage ขาดเมื่อ Atomic Red Team รันคำสั่งบน Linux (พบ 10 ต.ค. 2026) ⚠️

ART บน Linux รันผ่าน PowerShell (`pwsh`) ซึ่ง fork ตัวเองก่อนแล้วจึง exec `sh -c <คำสั่ง>`
Sysmon for Linux บันทึกเฉพาะตอน exec ตัวกลางที่ถูก fork จึงไม่มี ProcessCreate
→ คำสั่งที่ ART รันได้ `ParentProcessGuid = {000…}` และ PID ของ parent ไม่อยู่ใน log
→ lineage labeling ตามไปไม่ถึง seed → **คำสั่งโจมตีถูก label เป็น benign**
(ตัวอย่างจริง: `/bin/sh -c /tmp/evil.sh`, `cat /etc/issue`, `lsmod`, `arp -a`, `ps aux`)

ขนาดของปัญหา (process ที่ parent หายไป = orphan, ใช้ benign run เป็น control):

| Linux | process | orphan | label 1 |
|---|---|---|---|
| benign run (3) | 15,299 | 3 (0.02%) | 0 |
| attack run ชุดหลัก (5) | 13,330 | 2,475 (18.6%) — label 0 ทั้งหมด | 5,587 |
| matched (3) | 4,108 | 1,491 (36%) — label 0 ทั้งหมด | 839 |

orphan แทบไม่เกิดใน benign run จึงเกือบทั้งหมดมาจากการโจมตี → ประมาณขอบบนได้ว่า
**process การโจมตีฝั่ง Linux ราว 31% (2,475 / 8,062) ถูก label เป็น benign**
ฝั่ง Windows ไม่มีปัญหานี้ (ProcessCreate ครบทุกขั้น)

ผลต่อตัวเลขที่รายงาน:
- ตัวเลขฝั่ง Linux ทั้งหมด (F1, recall, zero-day) วัดเทียบกับ label ที่ขาด positive ไปบางส่วน
  — ส่วนหนึ่งของ "false positive" อาจเป็นการโจมตีจริงที่โมเดลจับได้ และ recall ถูกวัดบน positive ที่เหลือเท่านั้น
- อธิบายได้ส่วนหนึ่งว่าทำไม positive ฝั่ง Linux เหลือแต่สคริปต์ที่เขียนเองกับ harness และทำไม harness leakage ฝั่ง Linux หนักกว่า Windows
- การทดลอง cross-platform ชุด matched (ART ทั้งสองฝั่ง) **สรุปไม่ได้** — ฝั่ง Linux เหลือ positive ที่ไม่ใช่ harness แค่ 15 process

ทางแก้ที่ยังไม่ได้ทำ: ให้ labeler ผูก orphan เข้ากับ ART engine (`pwsh`) ที่ทำงานอยู่ในช่วงเวลาเดียวกันของ run
(parent PID > engine PID และเกิดระหว่างที่ engine ยังทำงาน) แล้วสร้าง Linux CSV ใหม่จาก raw log ด้วย `rebuild_dataset.py`
หรือเก็บ Linux ด้วย auditd/eBPF ที่บันทึก fork ด้วย
